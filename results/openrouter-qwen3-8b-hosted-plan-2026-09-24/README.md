# Hosted Qwen3-8B execution plan and stopped smoke tests

Current status: both P0 smoke modes stopped on upstream rate limits. See [smoke results](SMOKE_RESULTS.md) for exact coverage and sealed cost accounting. The following sections describe the preparation protocol.

The request model is `qwen/qwen3-8b`. Its sole public endpoint snapshot identifies `Alibaba | qwen/qwen3-8b-04-28` with provider tag `alibaba`; `qwen/qwen3-8b-04-28` is the endpoint name, not the OpenRouter request model. The [model API page](https://openrouter.ai/qwen/qwen3-8b/api) and saved [`endpoints-live.json`](endpoints-live.json) show $0.117 per million prompt tokens, $0.455 per million completion tokens, a 131,072-token context, and an 8,192-token completion limit. The saved catalog and endpoint snapshots were fetched by public GET on 2026-09-24; their hashes are in [`live-source-manifest.json`](live-source-manifest.json). They need live revalidation immediately before any paid call.

This is a distinct `json_object` condition. The endpoint advertises `response_format` and `reasoning`, but not `structured_outputs`. [OpenRouter’s Python API reference](https://openrouter.ai/docs/client-sdks/python/api-reference/chat) documents `{"type":"json_object"}`; the [model page](https://openrouter.ai/qwen/qwen3-8b/api) says its JSON output has no JSON-schema enforcement. The adapter therefore includes the existing four-field schema in the system instruction, validates strict JSON and the four allowed labels locally, and records invalid output without repair or retry. It never silently substitutes strict structured output or a different model. Explicit `reasoning.enabled` true and false are separate conditions; no named effort is requested.

Each request pins `provider.only=["alibaba"]`, disables fallbacks, requires parameter support, and caps provider prices at the observed rates. [OpenRouter provider-routing documentation](https://openrouter.ai/docs/guides/routing/provider-selection) describes these controls. Before a paid call, the adapter compares frozen experimental controls and exact prices with live catalog and endpoint data, while tolerating changes in uptime and latency telemetry. It records both full live snapshots and uses an already allocated partition of the shared budget ledger. Unknown charges leave a pending reserve and block further calls. Output and attempt files are exclusive; there is no automatic retry. A malformed JSON/schema answer with known billing is retained; continuation to the next unattempted input occurs only if that choice was recorded in the reviewed receipt. Service, identity, control, and unknown-cost failures stop. The existing strict `json_schema` paid runner and its phase-two controller do not admit this JSON-object condition; this adapter does not claim eligibility under those unchanged gates.

[`preview-v1/preview-manifest.json`](preview-v1/preview-manifest.json) freezes P0, P1 and P2 separately for reasoning off/on. Each condition has smoke3 (DEV-001–003) and full60 (DEV-001–060) **inputs-only** requests; the six full60 previews are plans, not observations. P1/P2 use the unchanged frozen prompt additions. No reference labels, API key, inference, budget reservation, or local model were used to build this preview. Before reading a key, the script requires a root review receipt bound to the exact preview, manifest, source snapshots and script hashes, then reconstructs all request bytes from the canonical unlabeled inputs, policy, schema and variant. Full60 also requires root approval of matching, hashed smoke evidence. An existing budget partition is required before any call. The offline preparation created no review receipt or partition. Root subsequently added smoke-only receipts and bounded partitions; those partitions are now sealed.

The reserved upper bound is `131072 × $0.117/M + 4096 × $0.455/M = $0.017199104` per call. Smoke3 plus full60 is 63 calls per condition; across six conditions, 378 calls have an aggregate *sum of independent upper bounds* of `$6.501261312`. This is neither a charge nor an upfront allocation: reservations settle sequentially against observed costs. The shared $5 cap and partition limits can stop execution before all planned calls; actual settled charges may be lower. Root must review scope and partition funding before inference.
