# Native Jev prompt and timing audit

The official Jev 1.13 baseline completed 60 valid development records. The page's **2.2 min** is the sum of 61 request attempts, including one failed transport call. It is not one inference. The official API response reports answers and token usage, but no server inference duration. We therefore cannot measure Jev's model-only time from these saved responses. See the [API response contract](https://docs.typesafe.ai/api), the [raw attempts](../results/openjev/typesafe-development-v2.jsonl), and the [continuation](../results/openjev/typesafe-development-v2-continuation.jsonl).

| Timing basis | Requests | Sum | Median | Nearest-rank p95 |
| --- | ---: | ---: | ---: | ---: |
| All development attempts | 61 | 131.883 s (2 min 11.883 s) | 1.316 s | 4.147 s |
| Successful requests | 60 | 101.141 s | 1.290 s | 4.112 s |
| Failed `DEV-046` transport attempt | 1 | 30.742 s | 30.742 s | 30.742 s |

The `DEV-046` failure was `RemoteDisconnected`. It accounts for 23.31% of the 131.883-second total. Its continuation succeeded in 0.808 seconds. The [reconciled 60-record file](../results/openjev/typesafe-development-v2-reconciled.jsonl) folds the failed and successful `DEV-046` durations into one 31.549-second record, preserving the total while producing a different 60-row median of 1.434 seconds. The [exporter](../scripts/build_public_explorer.py) correctly recovers the 61 raw attempts for the public median. The [site formatter](../public-site/app.js) renders any duration over 60 seconds in rounded minutes, causing the **2.2 min** display. The relevant per-request figures are in seconds; reporting them in milliseconds would be 1,316 ms median and 4,147 ms p95.

The original runner starts `elapsed_seconds` immediately before its HTTP call and stops after response parsing and budget settlement in [jev_benchmark.py](../scripts/jev_benchmark.py). That is client-observed request time plus small local work, including network delay. Neither the raw responses nor the [official response schema](https://docs.typesafe.ai/api) provide server or model-only milliseconds. TypeSafe's [building guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one) says most queries finish in about 100 ms; that general service claim does not measure this four-question, roughly 2,300-input-token benchmark path.

The 60 successful development responses report **140,260 input tokens** and **11,176 output tokens**. The failed call has no usage. At TypeSafe's published Jev 1.13 price of **$0.042 per million input tokens**, with output tokens free, the saved development estimate is **$0.005890920**; it is not a provider billing receipt. The failed call keeps its **$0.002123688** conservative unknown-cost reservation. Three earlier smoke requests add a separate **$0.000294294** token-price estimate. At this audit, the unchanged shared $1 ledger accounts for **$0.008308902**, leaving **$0.991691098** under its client cap. See the [model price](https://docs.typesafe.ai/models), [budget ledger](../results/typesafe-budget.jsonl), and [public resource export](../public-site/data.json).

## Native P1 and P2

The [TypeSafe API](https://docs.typesafe.ai/api) accepts `state` and typed questions. Each Choice has `instructions` and option `criteria`; both can hold structured descriptions. The [Choice guide](https://docs.typesafe.ai/primitives/choice) says questions in one call are evaluated independently, and the [state guide](https://docs.typesafe.ai/concepts/state) confirms all four questions see the same state. Jev is a decision model rather than a text-generating chat model, as [TypeSafe explains](https://docs.typesafe.ai/introduction/coding-agents). It has no system-message role or generated JSON to prompt. A useful native comparison changes the question instructions, not the chat prompt.

The separate [native runner](../scripts/jev_native_prompt_variants_v1.py) keeps the P0 endpoint, pinned `jev-1.13.0`, one feedback per call, complete policy, four Choice IDs and order, choice criteria and labels, parsing, and retry policy. P1 appends the same classifier framing to each question's instruction. P2 retains that P1 addition byte-for-byte and appends a field-specific policy procedure. Its four procedures are evaluated in parallel, not as a sequential global decision tree. Only `questions.*.instructions` changes. This is a **native question-instruction sensitivity** experiment, distinct from the generative P1/P2 system-prompt protocol in [PROMPT_VARIANTS.md](PROMPT_VARIANTS.md).

The [input-only manifest](../results/jev-native-prompt-variants-v1/input-only-manifest.json) binds all 60 request hashes to the existing P0 payload hashes and source hashes. It includes no reference labels or predictions. Preparation checks the saved P0 request hashes; live preflight checks only the immutable baseline file hash and newly composed requests. The planned conservative reservation ceilings for three smoke plus 60 development requests are **$0.144648504 for P1** and **$0.155211336 for P2**, or **$0.299859840 combined**. These are client planning bounds, not expected provider charges. The runner shares the existing locked $1 ledger, preserving unknown prior reservations.

Each condition requires a hash-bound plan review receipt before its three-case smoke. Development requires three valid saved smoke responses and a separate inspection receipt bound to those exact smoke bytes. The runner writes request payloads and hashes, raw responses, reported input/output/reasoning token fields when available, the input-token cost estimate and unknown-billing flag, a client HTTP-call duration, and an explicit `null` server inference duration. It writes durable started, finished, and terminal journal entries. A missing terminal entry marks an interrupted run for reconciliation. Service errors and unknown-cost attempts stop the condition. No P1/P2 inference had been performed when this audit was written. References remain offline for later evaluation.
