# Mistral Small 4 119B execution candidate, 29 September 2026

The [execution controller](../scripts/mistral119_fresh_repeat_execution.py) is an offline, **unapproved and unfunded** candidate for the two Mistral119 configurations in the [six frozen plans](MISTRAL119_FRESH_REPEAT_ADMISSION_2026-09-29.md). Its [separate execution manifest](../results/repeatability-v1/mistral119-fresh-matched3-v1/execution-manifest.json) binds both configurations, all three passes per configuration, this controller, the planner, the tests, and the reviewed shared request, transport, and budget code. Freezing the manifest made no provider request and allocated no budget. The historical five `none` and three `high` DEV-001 HTTP 429 failures remain earlier, ineligible attempts; this controller neither imports them as a pass nor retries them.

The controller privately loads the [reviewed Qwen27 lifecycle](../scripts/qwen27_fresh_repeat_execution.py) and substitutes only Mistral119's frozen plans and stage admission checks. It leaves the Qwen27 module and its plans unchanged. A stage is admitted only with a separate root review receipt naming the exact configuration, pass, condition, `smoke` or `development` stage, controller and execution-manifest hashes, all three plan hashes for that effort, the allocated child manifest path and hash, partition ID, master ledger, and the **actual child cap**. The receipt's cap must equal the child manifest cap and the opened child ledger cap, and fit at least one $0.04177920 full-context reservation. There is no default cap or automatic increase. The present six plans contain no known-charge proxy or proposed whole-series cap, so an allocation and each stage review remain future decisions under the current aggregate budget.

Before key access or a phase claim, the controller verifies the receipt and plan, checks earlier conditions and passes for strict closure, reads the current unauthenticated [OpenRouter model catalog](https://openrouter.ai/api/v1/models) and [exact endpoint catalog](https://openrouter.ai/api/v1/models/mistralai/mistral-small-2603/endpoints), and compares the saved Mistral `mistral/zdr` route, model, status, context and token limits, supported controls, and price. It rebuilds every development request for the selected condition and requires exact payload equality, including the distinct `none` or `high` reasoning controls. Catalog agreement is an admission check, not proof that the provider can serve a completion: the [readiness evidence](MISTRAL119_REPEAT_READINESS_2026-09-29.md) records 429 responses despite available-looking metadata.

Each stage takes the actual child-ledger lock before reading a key or making a claim. It reserves the full $0.04177920 for each request atomically, writes request intent and attempt evidence, saves at most 16 MiB of HTTP status, selected headers, and response bytes durably **before JSON parsing**, then settles a known charge or retains the entire unknown bound. A malformed 200, HTTP error, invalid result, billing failure, or insufficient next reserve stops the stage without replay or provider substitution. The three smoke responses require strict, known-billed closure and a separate inspection receipt before development. Every later condition and pass requires strict predecessor closure. Attempts and raw responses may contain private provider fields; the series-specific `.gitignore` rules exclude both `*.responses.jsonl` and `*.attempts.jsonl` at all stage paths. Public reporting needs a separately reviewed sanitized projection.

The [offline tests](../tests/test_mistral119_fresh_repeat_execution.py) exercise both exact route/effort checks, six-plan binding, an actual temporary child allocation and lock, three smoke calls followed by inspection and 60 development calls, no replay, receipt/cap drift before key access, and malformed HTTP 200 raw capture with a retained full unknown bound. These are mocked provider calls and temporary ledgers only. They establish controller behavior, not current serving capacity, future cost, or funding for 567 calls per effort. A subsequent root review must choose and fund an exact stage cap, assess the 429 capacity evidence, create a stage-specific receipt, and independently approve dispatch. Completing one smoke would not itself approve its development stage.
