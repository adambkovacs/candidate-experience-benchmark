A second and third pass would help distinguish prompt effects from run-to-run variation on the existing 60 development records. Three total passes per eligible configuration and condition are a useful diagnostic, but too few to support precise confidence intervals or a claim of generalization. ## Establish a comparable first pass

Before scheduling repeats, audit each exact model configuration separately. Pass one must have all 60 development positions accounted for and enough saved evidence to reconstruct the client requests, prompt versions, batch membership and order, settings, outcomes, and failure handling. A complete set of saved responses alone does not prove that its P0, P1 and P2 form a controlled triple. Historical P0 reuse, material request changes, interrupted runs, continuations, unknown in-flight attempts, provider failures, and opaque rendering can make an otherwise useful result ineligible for a strict repeat comparison. Preserve such results as descriptive observations and state the specific missing or changed control. The [current status](MVP_STATUS.md) and [existing paired reports](../results/prompt-comparison-v1-2026-09-24/paired-reports/) show why eligibility has to be decided per configuration rather than for the whole roster.

If an eligible first pass does not exist, any future matched run starts a new three-pass series. Do not relabel a heterogeneous historical run as repetition one or rerun an already completed configuration merely to fill this design without documenting that fresh-series decision in the schedule. The user has authorized repeats for all three prompt conditions; another scope approval is not required within the agreed limits. The previously accepted Codex CLI patch-version change alone does not disqualify a baseline or justify rerunning it.

## Freeze and run design

For an admitted series, freeze the same 60 input IDs, provisional references, labeling rubric, schema, P0 baseline and P1/P2 prompt bytes and role placement. Freeze the exact configuration: model and provider endpoint or local artifact, version where exposed, runtime, quantization and hardware where applicable, reasoning effort, sampling, context and output limits, response format, parser, timeout, retry policy, and batch size. Keep the P0 context unit: one fresh context per record for individual requests, or one fresh context per identical batch for batch-of-ten requests. Within each pass, P0/P1/P2 must use identical record membership, order and batch boundaries. Never mix individual and batched outcomes in a matched series.

Use independent fresh contexts for each request and pass. Predeclare a balanced rotation of condition order across the three passes, such as P0-P1-P2, P1-P2-P0 and P2-P0-P1, then freeze the schedule before inference. Record actual launch times and any departures. If the original pass used another order, construct a documented rotation around its observed order rather than claiming it was counterbalanced prospectively. The [global roster freeze and schedule](../results/prompt-comparison-v1-2026-09-24/roster-freeze.json) govern the original pass; a repeat schedule would need its own versioned schedule and evidence.

Predeclare the seed policy per configuration. Reusing the same seed tests backend reproducibility under fixed controls; varying seeds tests sampling sensitivity. Keep those analyses separate and do not switch policy between passes silently. Record the requested seed and the effective seed if the surface exposes one; write `unknown` where it does not. Log exact model identifier, provider, endpoint, revision, runtime/client version, artifact hash, quantization, hardware, and visible controls for every pass. A changed model or serving revision is a separate configuration unless equivalence is explicitly justified in the report. Even an unchanged advertised model ID may conceal provider-side drift, which must remain an observational limit. References stay out of inference requests and are read only by the offline scorer.

Each new condition still needs a three-response smoke and inspected admission before its 60-record development pass, as in the [prompt protocol](PROMPT_VARIANTS.md#controls-and-execution). Count smoke usage, time and expense separately. Do not silently repair invalid outputs or replay ambiguous attempts.

## Analysis and decision gate

For each exact configuration and condition, report the three pass-level values and their mean and range for all-four agreement and each field's agreement against the unchanged provisional references. Show the per-record label flip rate between passes for each field, plus the fraction of records whose four-field vector changes. Compute each flip rate only over records with comparable valid labels in the compared passes, and report that denominator and the IDs excluded for missing or invalid outcomes. Keep the record IDs so unstable cases can be inspected. Compare P1 and P2 with P0 within each pass first, then show the spread of those paired differences across passes. Keep invalid outputs, refusals, timeouts, service errors, unknown started attempts and never-sent positions in separate counts with the 60-position denominator. Do not score a missing response as a label or hide it by averaging only valid outputs. Report tokens, request-unit timing and actual or accounted cost separately; batch duration divided by ten is an amortized share, not ten independent latency measurements.

Three passes over the same 60 synthetic, provisionally labeled records show repeatability on those records only. They do not create 180 independent cases, resolve label uncertainty, or yield narrow population confidence intervals. Preserve scenario-family dependence in any descriptive uncertainty summary. A claim that one prompt generalizes better still requires separately authorized held-out data and independent reference review, as the [project plan](PLAN.md) describes.

Before any launch, produce a per-configuration estimate from observed request and token usage, including smoke calls, expected retries, and conservative unknown-charge reservations. Check subscription quotas and the remaining aggregate OpenRouter $10 and TypeSafe $1 caps against their authoritative ledgers and the [project scope](../AGENTS.md). Do not enable paid overage, raise a cap, or exceed the existing spending authorization. Admit a repeat only after its first-pass eligibility, exact controls, schedule, provider availability, and budget estimate have been reviewed.
