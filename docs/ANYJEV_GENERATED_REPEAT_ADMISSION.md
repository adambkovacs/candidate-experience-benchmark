# AnyJev generated-control repeat admission

The proposed local study has three new passes over P0, P1, and P2 in the order P0/P1/P2, P1/P2/P0, then P2/P0/P1. It uses the same 60 input-only development records and the Qwen3-0.6B weights as the separate native AnyJev readout. This is HF text generation with a JSON instruction in the system message, not native raw, L0, L1, or L2 decision scoring. The [prior admission audit](GENERATED_SPECIALIST_REPEAT_NEXT_ADMISSION_2026-09-28.md) records why the saved P0, P1, and P2 outputs remain historical observations rather than a proven matched first pass. A suitable exact hosted route was not identified there; this controller stays local.

The offline [controller](../scripts/anyjev_generated_repeat_admission.py) reuses the historical [message composer and strict parser](../scripts/anyjev_generation_control.py). It verifies the local Qwen artifact revision `c1899de289a04d12100db370d81485cdf75e47ca`, every declared artifact file by content hash, and the saved [exact-token preflight](../results/anyjev-generated-phase2-token-preflight-2026-09-23.json). The new plan records every condition's 60 message hashes, rendered prompt hashes, input-token ID hashes, and token lengths. It checks P0/P1/P2 reconstruction against that preflight and the three saved development files. Historical valid counts are P0 0/60, P1 0/60, and P2 30/60. Fenced JSON stays invalid; the controller does not strip fences or repair predictions.

Runtime controls are local MPS BF16 with no quantization, `do_sample=false`, `enable_thinking=false`, full input limit 4,096, output limit 4,096, and model context 40,960. The tokenizer applies the native chat template with a generation prompt and no added special tokens. Before every future call the controller compares the actual message bytes, rendered prompt, token IDs, and tensor input with the frozen request. It never reads reference labels. The saved P0 request hash is not a saved copy of its generated messages or rendered prompt; the plan therefore names `fresh1`, `fresh2`, and `fresh3` rather than relabeling history.

Each condition has an exclusive three-record smoke and 60-record development stage. The controller takes the shared GPU host lock, checks the exact reviewed receipt and prior completed conditions, writes a durable claim, then loads the model. It fsyncs per-record `request_started` before generation. It saves raw token IDs, decoded text, finish reason, EOS IDs and timing before applying the strict parser. Invalid and length-stopped outputs remain saved invalid positions. A generation or capture failure leaves a started unknown and stops the stage; no stage or record is automatically replayed. Development requires a separate receipt bound to an inspection of all three smoke raws. Inspectors must explicitly accept intrinsic invalid outputs unchanged and state why. Local cost and pure model-only inference time are not inferred from client timing.

Root review approved the offline controller with no confirmed blocking finding. The manifest was frozen with SHA-256 `7f6a55b26129d8a742e03ecf7e1d2477bbd9b7b2bdde41d4f6a8fa96104f095b`. No stage receipt has been issued, and no model weights were loaded or inference performed. The six focused [tests](../tests/test_anyjev_generated_repeat_admission.py) use a fake tokenizer and model to check rotation, raw-before-parse, fenced invalids, interrupted starts, receipt gates, and predecessor fences. Root review of the controller and exact manifest is required before any local GPU stage can be admitted.
