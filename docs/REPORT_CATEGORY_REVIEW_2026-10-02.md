# Report category and chart review, 2 October 2026

The [Clef Decision Model Leaderboard](https://clef-evals.workers-ai-mle.workers.dev/) is a useful design reference, not a source of scores for our 60 fictional candidate-experience reviews. I inspected its leaderboard, [charts](https://clef-evals.workers-ai-mle.workers.dev/#figures), and [methodology](https://clef-evals.workers-ai-mle.workers.dev/#methodology) in the live browser on 2 October. Its 73-entry table is a snapshot of a different decision benchmark. The site says its Cloudflare results are self-reported; the other entries come from the community Jev Decision Index. The site also warns that Cloudflare and community latency measurements use different hardware. Importing its ranks or drawing one cross-hardware speed frontier for this project would imply comparability that we have not established.

## What the reference does well

The opening plot places decision score against median latency and labels selected models rather than every point. A compact horizontal bar chart shows the top 15, while the full table carries model, score, five task areas, latency, calibration, and parameter columns. Its visible leaders include Decider 35B, Jevfire, Winnow-12B, Clef Flash, Jev, and Clef; the full table also contains community open-model variants. This is a research roster, not evidence that any of these additional models ran in our project. The charts tab adds a log-scale quality-versus-latency scatter, a selectable five-axis area profile, and calibration versus quality. Hover details and a separate methodology page let readers trace what each mark means. The pale background, restrained orange/black/blue accents, and sparse callouts keep a dense roster readable. These are presentation ideas; the [board's method and weights](https://clef-evals.workers-ai-mle.workers.dev/#methodology) do not define our rubric.

For this report, lead with **coverage and measured outcomes**, because an attractive ranking would hide unfinished phases. The existing [repeat findings](LEGACY_QWEN_REPEAT_FINDINGS_2026-10-02.md) show why validity and correctness must have different marks: one exact Qwen3 0.6B HTTP configuration produced 60 schema-valid P0 answers but no four-field exact matches in its first pass. The chart and table should expose the configuration and denominator behind each mark.

| Suggested view | Encoded measures and disclosure | Why it helps |
| --- | --- | --- |
| Configuration coverage matrix | Rows are exact model + interface + route configurations; columns are P0/P1/P2 and fresh pass. Each cell shows closed, stopped, partial, or unsent status and attempted/valid/invalid counts. | Prevents a completed subset from looking like a complete roster. |
| Validity versus four-field agreement | For closed 60-record phases, plot valid/60 against all-four agreement/60. Use separate P0/P1/P2 panels, category color and interface shape; tooltip gives exact phase and source. | Shows strict-output failures and valid-but-wrong classifications without merging them into one score. |
| Four-field diagnosis | Per-field fixed-denominator bars with an optional prediction/reference confusion grid. Keep provisional reference labels named as such. | Exposes class collapse that a single exact-match rate conceals. |
| Repeat stability | Show classification flips on shared-valid IDs beside validity on all 60 positions, only after at least two closed passes. | A stable answer can still be wrong, and missing outputs must not disappear from the denominator. |
| Latency and calibration, when eligible | Show client median/p95 timing within comparable runtime and route groups. Show calibration only for retained, native per-option probabilities with a defined target and denominator. | Avoids treating client wall time as pure inference or generated text as calibrated probability. |

## Category rule

Use the three requested categories for **checkpoint specialization**, and keep **output interface** and **execution surface** as independent fields. Prompt wording, P0/P1/P2, host, and JSON parser do not turn a general model into a task-trained model. A native probability readout does not by itself prove that the underlying weights were trained for decisions. Store the exact checkpoint or vendor model ID and a source link for each assignment. If training provenance is unavailable, show “classification pending source” rather than infer it from the product name.

| Category | Inclusion test | Current roster mapping and evidence |
| --- | --- | --- |
| **General LLM** | A broadly useful generative checkpoint, including one prompted for four labels or read through a decision adapter without changed checkpoint weights. | Claude, Codex/GPT, Gemini, Qwen, Gemma, DeepSeek, and Mistral families in the [roster](MVP_ROSTER_ACCOUNTING.md). The independent [OpenJev](https://github.com/razorback16/openjev) server reads a DiffusionGemma checkpoint and also provides generated controls; this is a general backbone with two interfaces, not two training categories. [SemIf](https://github.com/TheoLeeCJ/SemIf) reads declared-option scores from frozen Qwen weights. [AnyJev L0](ANYJEV_L0_NATIVE_P0_REPEAT_ADMISSION_2026-09-28.md) reads a pinned Qwen3 0.6B checkpoint. AnyJev's separately [fitted L2 head](ANYJEV_CALIBRATION_NEXT_ADMISSION_2026-09-28.md) is a task-adapted **system**, but it does not by itself establish that the LLM checkpoint was fine-tuned; record that adaptation separately. |
| **Task-fine-tuned LLM** | An LLM-derived checkpoint whose weights were trained for a bounded downstream label or decision task, rather than merely prompted or wrapped. | [AlexWortega/openjev](https://huggingface.co/AlexWortega/openjev) is based on Qwen3.5 and trained as a three-label NLI sequence classifier. Its entailment/contradiction/neutral task is not identical to our four reference fields; the adapter's option scoring belongs in the interface field. A proposed model such as [Tev](DECISION_MODEL_ROUTE_AUDIT_2026-09-30.md) should enter this row only after its exact checkpoint and training claim are verified; it is not an existing run. |
| **Dedicated classification/decision model** | A model presented and trained for typed classification or declared-choice decisions as its primary task, rather than open-ended generation. | [TypeSafe Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) exposes typed probability decisions; alternative hosts remain routes for the same model. [Laya](https://huggingface.co/convaiinnovations/laya) describes a non-autoregressive decision model with typed questions and probabilities. [Kev-4B](https://huggingface.co/jaredpalmer/kev-4b) uses a frozen Qwen backbone plus trained LoRA and pointer head to make typed decisions, so its *system* belongs here even though its backbone is an LLM. [Cloudflare Clef and Clef Flash](https://blog.cloudflare.com/clef-decision-models/) are vendor-described decision models with typed answers and probabilities; each has completed a three-review smoke test here. Full 60-review results are not yet available; the smoke tests are excluded from the result rankings. |

The [rules-v1 baseline](MVP_ROSTER_ACCOUNTING.md) is deterministic software, not a model in any of the three categories. A fourth data state, “classification pending source,” is only a provenance gap and should never be plotted as a fourth model type. Avoid counting routes, prompt conditions, generated and native readouts, or fitted heads as separate underlying models. Those distinctions remain visible in configuration labels.

An implementable row can carry `category`, `categoryEvidence`, `checkpoint`, `interface` (`generated_text`, `native_choice_probabilities`, `nli_scoring`, or `rules`), `adaptation`, `executionSurface`, and `configurationId`. This allows category filters and chart symbols without losing exact experimental identity. Reconcile these fields against the [current goals](CURRENT_GOALS.md) and source-bound result feeds before changing the public site; this document makes no new benchmark measurement or roster admission.
