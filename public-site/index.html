How reliably does AI read candidate feedback?

We gave AI models the same 60 fictional candidate comments and asked four questions about each one. The totals are only a start. See the individual answers, what changed with new instructions, and what happened when we asked again.

01 / A specialist alongside chat models

Jev matched 54 of the 60 comments. Six had a disagreement.

Jev 1.13 is a specialist decision model. We asked it the same four questions through its native Choice API, which chooses between supplied answers.

In this base-task run, every response could be scored. Six comments had at least one answer that differed from our reference. Open those comments before treating 54/60 as a verdict.

For a recruiting team: check the type of mistake. Missing a follow-up request and misreading praise can lead to different actions.

02 / Longer instructions did not consistently help

With decision-tree instructions, scores were lower in 21 of 39 comparisons.

We tried three prompt versions: the base task (P0), more explicit classifier instructions (P1), and a step-by-step decision procedure (P2).

Moving from P1 to P2 improved four setups, left 14 unchanged and lowered 21 scores in the audited comparison. A setup means a particular model, route and settings.

For people designing a workflow: test added instructions on examples from your own work. More detail is not evidence of a better result.

03 / The same instructions can give different answers

We asked again. Eleven comments got different answers.

In two Gemma E2B thinking-on runs with the same P1 instructions, the score moved from 36 to 39 out of 60. Both runs returned 60 responses we could score.

Four comments gained a full match with the reference; one lost it. Other answers changed without changing whether all four matched.

For leaders assessing a pilot: ask for repeat results and examples of changed answers. A three-point difference on one run can hide variation.

Put the findings to work

Use this study to ask better questions about your own AI pilot.

These findings are specific to a small, fictional set. They can help shape a test; they cannot choose a production system for you.

Recruiting, HR and L&D teams

Write down what each label should mean. Review sensitive and ambiguous comments together. Check whether errors would send work to the wrong person.

Business and transformation leaders

Ask what was tested, how often, and against whose answers. Compare the mistakes and the measured cost, not just a single total score.

Builders and technical teams

Keep the model, provider, settings and input groups fixed when comparing prompts. Save failures. Score against reference answers only after inference.

Method and limits

How we ran the test, and what it cannot tell you.

The comments are fictional and the reference answers are provisional. These scores show agreement within this development test.

How the test was scored

Prompt versions: P0 is the base task; P1 and P2 add different instructions. Every score is out of 60, even when a run saved fewer responses. The same AI assistant drafted and reviewed the reference answers. No independent person checked them.

Time: Server inference time appears only when a provider reports it. The technical run detail shows recorded client request durations, their sum and the number of timed requests. Some requests classified one comment; others classified a batch. The sum does not show how long concurrent work took from start to finish. Local times reflect the test machine and workflow.

Cost: Reported API charges, price estimates and possible charges without a known bill are labeled separately. Subscription fees are not split across runs. An API price estimate is not an observed charge.

Questions you may have

What do “model”, “prompt” and “run” mean?

The model is the AI system. A prompt is the set of instructions and the comment it receives. A run is one recorded attempt to classify this set of comments using a particular setup.

What are tokens, and why do they matter?

Tokens are small pieces of text a model reads or produces. Hosted services often price requests by input and output tokens. Extra reasoning can add output tokens even when the final answer is short.

Did every model process comments in the same way?

No. Some calls contained one comment; subscription runs sometimes used batches. Specialist APIs returned choices directly. Local runs used this project's machine. We keep these differences visible because they affect comparisons.

What were the models allowed to see?

The comment and the task instructions, including the label definitions. They did not receive the reference answer or another model's previous prediction. We compared outputs with the references afterward.

Does a valid response mean the answer matched?

No. Valid means the response followed the format needed for scoring. Agreement is counted separately against the saved reference answers.

Do score changes show that one prompt is better?

You can compare saved outcomes, but differences in where and when runs were made, missing records, and other settings make it hard to attribute a score change to the prompt alone. Five earlier local Qwen comparisons lack logs for the base runs. Their comparison reports show the saved changes and explain the missing evidence.

Why can a complete run have invalid responses?

Complete means a response was saved for each of the 60 comments. Some saved responses did not follow the required format, so they could not be scored.

Why is a price missing?

Some services do not report a charge for each run. An unavailable charge does not mean the run was free. Estimates and upper bounds are labeled separately.

Can I use these scores to choose a hiring tool?

No. This small fictional set and its provisional answers do not measure performance with real candidates or the effect of using a model in hiring.
